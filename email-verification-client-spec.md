# Client Spec — Email Verification

Спецификация для мобильного клиента (`com.boiko.english_learning`): подтверждение email кодом из письма и блокировка синхронизации до подтверждения.

> Касается только аккаунтов **email + пароль**. Вход через Google уже считается доверенным (email подтверждать не нужно).

---

## 1. Общая логика

1. Пользователь регистрируется (`POST /api/auth/register`) → бэк создаёт аккаунт, **сразу отправляет код на email** и возвращает обычный `AuthResponse` (`accessToken` + `refreshToken`). Пользователь уже залогинен, но `user.emailVerified == false`.
2. Клиент показывает экран ввода кода (6 цифр). Код действует **60 секунд**.
3. Пользователь вводит код → `POST /api/auth/verify-email`. При успехе email считается подтверждённым.
4. Пока email не подтверждён — **синхронизация недоступна**: `POST /api/sync` и `GET /api/sync/bootstrap` возвращают `403 EMAIL_NOT_VERIFIED`.
5. Если код истёк/потерян — `POST /api/auth/resend-verification` (есть кулдаун между отправками).

Все защищённые ниже эндпоинты требуют `Authorization: Bearer <accessToken>` (тот же токен, что выдан при регистрации).

---

## 2. Эндпоинты

### 2.1. POST /api/auth/verify-email — подтвердить email
Auth: **Bearer**.

Request:
```jsonc
{ "code": "123456" }
```
Response 200:
```jsonc
{
  "emailVerified": true,
  "expiresInSeconds": 0,
  "resendAvailableInSeconds": 0
}
```

### 2.2. POST /api/auth/resend-verification — переотправить код
Auth: **Bearer**. Тело не требуется.

Response 200:
```jsonc
{
  "emailVerified": false,
  "expiresInSeconds": 60,          // сколько действует новый код
  "resendAvailableInSeconds": 30   // через сколько можно снова запросить
}
```

### 2.3. Изменения в существующих эндпоинтах
- `POST /api/auth/register` — поведение прежнее (возвращает `AuthResponse`), но дополнительно триггерит отправку кода. В ответе `user.emailVerified == false`.
- `GET /api/auth/me` — используйте `emailVerified`, чтобы понять, нужен ли экран подтверждения (например, после перезапуска приложения).
- `POST /api/sync`, `GET /api/sync/bootstrap` — пока email не подтверждён, отдают `403` c `code = EMAIL_NOT_VERIFIED`.

## 3. Формат ошибок

Единый формат (как и во всём API):
```jsonc
{ "error": { "code": "INVALID_CODE", "message": "Confirmation code is incorrect" } }
```

| code | HTTP | Когда | Что делать на клиенте |
|---|---|---|---|
| `INVALID_CODE` | 422 | Неверный код | Показать ошибку, оставить экран ввода, дать ещё попытку |
| `CODE_EXPIRED` | 422 | Код истёк (прошло >60 c) | Предложить «Отправить новый код» |
| `CODE_NOT_FOUND` | 422 | Активного кода нет (не запрашивался / уже использован) | Предложить «Отправить новый код» |
| `TOO_MANY_ATTEMPTS` | 429 | Превышен лимit неверных попыток (5) | Код аннулирован → «Отправить новый код» |
| `EMAIL_ALREADY_VERIFIED` | 409 | resend, когда email уже подтверждён | Закрыть экран подтверждения |
| `RATE_LIMITED` | 429 | resend раньше окончания кулдауна | Заблокировать кнопку до `resendAvailableInSeconds` |
| `EMAIL_NOT_VERIFIED` | 403 | sync без подтверждения | Не синхронизировать, показать экран подтверждения |

Параметры по умолчанию (бэк, могут отличаться от окружения):
- Длина кода: **6 цифр**.
- Время жизни кода: **300 секунд**.
- Кулдаун повторной отправки: **30 секунд**.
- Максимум неверных попыток: **5** (потом код аннулируется).

## 4. Рекомендуемый клиентский флоу

```
register() -> AuthResponse (emailVerified=false)
   -> экран "Введите код из письма" + таймер 60с (expiresInSeconds)
        -> verifyEmail(code)
             200 emailVerified=true -> закрыть экран, включить синхронизацию
             422 INVALID_CODE       -> показать ошибку, оставить ввод
             422 CODE_EXPIRED/CODE_NOT_FOUND -> показать "Отправить новый код"
             429 TOO_MANY_ATTEMPTS  -> показать "Отправить новый код"
        -> resendVerification() (кнопка активна по таймеру resendAvailableInSeconds)
             200 -> сбросить таймер 60с, очистить поле ввода
             429 RATE_LIMITED -> держать кнопку заблокированной
```

Дополнительно:
- **Таймеры локальные.** Считайте обратный отсчёт от `expiresInSeconds` / `resendAvailableInSeconds`, полученных в ответе. По истечении кода предлагайте только переотправку (повторная попытка с истёкшим кодом вернёт `CODE_EXPIRED`).
- **Кнопка resend** заблокирована, пока идёт кулдаун; по `RATE_LIMITED` оставляйте заблокированной (без краша).
- **Синхронизацию не запускайте**, если `emailVerified == false`. Если планировщик/воркер всё же дернул sync и получил `403 EMAIL_NOT_VERIFIED` — тихо пропустите цикл (не logout) и покажите подсказку о подтверждении.
- **Состояние подтверждения** определяйте по `user.emailVerified` из `register` / `GET /api/auth/me`. После успешного `verify-email` сразу разрешайте синхронизацию.
- **Google-вход** не требует этого флоу (`emailVerified` приходит уже `true`/управляется провайдером) — экран подтверждения не показывать.

---

## 5. Чек-лист приёмки (клиент)
- [ ] После `register` показывается экран ввода 6-значного кода с таймером 300 c.
- [ ] `verify-email` с верным кодом → `emailVerified=true`, синхронизация включается.
- [ ] Неверный код → `INVALID_CODE`, экран остаётся, попытки ограничены (после `TOO_MANY_ATTEMPTS` — только resend).
- [ ] Истёкший код → `CODE_EXPIRED`, предлагается resend.
- [ ] Кнопка resend учитывает кулдаун (`resendAvailableInSeconds`, `RATE_LIMITED`).
- [ ] Sync не выполняется до подтверждения; `403 EMAIL_NOT_VERIFIED` обрабатывается без logout.
- [ ] Для Google-аккаунтов экран подтверждения не показывается.
